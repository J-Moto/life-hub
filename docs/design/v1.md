## 1. What v1 is (and isn't)

**Is:** one private web page showing five things:
1. Today's calendar
2. TickTick **Today** list with checkboxes
3. A box to add a task to **Next**
4. Weekly habit percentages
5. A **Restart** button

**Isn't (later versions, not v1):** the smart layer (section 7), editing task text, links to Claude projects, a chat panel, scrap pad, clickable flowcharts, project planner, smart devices, finances, n8n, NAS integration, phone app, notifications.

**Why it exists:** a portfolio project that shows real OAuth, security and testing work. It is not a productivity fix. The system already works without it.

**Hard rules (from Life Hub design notes):**
- Reads TickTick and Google Calendar. **Stores none of your tasks, events or habit data.** The only things kept are encrypted tokens and a 10-minute login state. If the hub is deleted, nothing is lost.
- No streaks anywhere. Percentages only, with a ~70% target line.
- No notifications in v1. Few alerts, or they stop working.
- Nothing carries over as debt. Restart sends Today's leftover tasks back to Next.

## 2. Decisions

### A. The Today list

| # | Question | Decision |
|---|---|---|
| A1 ✅ | What counts as "Today"? | The TickTick **project named "Today"**, not TickTick's smart Today filter. The project is found by its **ID in config**, not by name. Show its top-level unfinished tasks in TickTick's manual order (`sortOrder`). Checklist items inside a task aren't shown. Tasks due today in other projects aren't shown. |
| A2 ✅ | What if Today has more than 3 tasks? | Show them all, plus one plain count line, only when over 3: "4 today · limit 3". Normal text color, no red, no warning icon. |
| A3 ✅ | What does checking a box do? | Marks the task complete in TickTick. The row fades, and **Undo** shows for 5 seconds before the request is sent, so a mis-tap costs nothing. Each task has its own timer. If the page is closed or hidden during the 5 seconds, the completion is sent immediately. If the request fails, the row comes back with a quiet "didn't save" note. (TickTick documents no way to un-complete a task, so waiting before sending is the undo.) |
| A4 ✅ | Can I edit or reorder tasks here? | **No.** Editing stays in TickTick. v1 only reads and completes. Tapping a task's text does nothing: no detail view, no link out. Editing task text on the hub is on the later list (section 6). |
| A5 ✅ | Show priority-tag tasks differently? | Yes. A small text tag in front, with the prefix hidden. The prefix (`JOB:` to start) and its label ("JOB") **come from config, not code**, so the tag can become `CLASS:` or `WORK:` later. **One tag at a time in v1**; several tags at once wait for the smart layer's auto labels (section 7). The match is the prefix at the start of the title, any letter case. |
| A6 ✅ | What if Today is empty? | One neutral line: "Today is clear." No button, no prompt to add more. The hub can't tell "all done" from "never picked", and the line covers both. |

### B. Add to Next

| # | Question | Decision |
|---|---|---|
| B1 ✅ | What does the box do? | Creates a task in the **Next** project with the text as typed, with leading and trailing spaces trimmed. An empty box does nothing. The button is disabled while sending, so a double tap can't create two tasks. On success the box clears and a quiet "Added to Next" shows for a few seconds; the hub doesn't show the Next list. On failure the text stays in the box with a quiet "didn't save" note. |
| B2 ✅ | Help with the first-step format? | Placeholder text: `open resume doc (done = 1 application submitted)`. A priority-tag toggle (labelled **JOB** to start; prefix and label come from config, see A5) adds the prefix in front unless the text already starts with it, and switches off after each add. No other validation. |
| B3 ✅ | Add to Today or Someday too? | **No.** Only Next. Today is chosen in the morning routine, and Someday ideas go in from chat. |

### C. Weekly habit %

| # | Question | Decision |
|---|---|---|
| C1 ✅ | Which habits? | The three: Job action, Phone-free morning, 15-min home reset. Their IDs **and display names are stored in config**, because the API habit list can leave some out. The section then needs one request (the check-ins). Renaming a habit in TickTick doesn't change the hub until config changes. |
| C2 ✅ | What's a "week"? | **Monday–Sunday**, so the number is complete at the Sunday Reset. "Today" and the week edges are worked out in `America/Indiana/Indianapolis` time. |
| C3 ✅ | How is % calculated? | **% so far this week.** A day counts as done when its check-in `value` reaches its `goal`. Percentage = done days ÷ (days already finished this week + today, if today is done). The number never drops for a day that isn't over. Monday before any check-in shows "—", not 0%. By Sunday evening this equals the full-week number, so there is no separate full-week figure. |
| C4 ✅ | How is it shown? | One bar per habit with a thin line at 70%, plus the numbers as text: "75% · 3 of 4 days". The bar doesn't change color below 70%. No streak counts, no flames, no red. |
| C5 ✅ | What if OAuth can't read habits? | TickTick's docs list only `tasks:read` and `tasks:write` and don't say what the habit endpoints need. Test with a real token as soon as TickTick login works (build step 4). If the OAuth token is refused, **habit % leaves v1.** No personal API token: it's a second, broader credential. |
| C6 ✅ | Check in habits from the hub? | **No.** Habits are read-only in v1. Check-ins happen in TickTick. (The API documents no way to undo a check-in.) |

### D. Restart

| # | Question | Decision |
|---|---|---|
| D1 ✅ | What does Restart do? | (1) Moves every unfinished Today task back to **Next**, (2) adds **one Minimum task** to Today, (3) shows "The system is back on." Rules: the Worker re-reads Today at the moment of Restart and doesn't trust the page's list. Any completion still inside its 5-second undo window is sent first, so a just-checked task is completed, not moved. If the Minimum task is already in Today (same title), it stays and no second one is added, so pressing Restart twice changes nothing. The move runs first, then the add; if the add fails, the message says so ("Moved 3 tasks. Couldn't add the Minimum task.") and pressing Restart again only does the missing part. With Today already empty, Restart just adds the Minimum task. |
| D2 ✅ | Which Minimum task? | **One fixed line from config**, no tidy option and no choice. Starting text: `JOB: open job board, save 1 posting (done = 1 saved)`. The text is configurable, not hardcoded. |
| D3 ✅ | Confirmation? | One confirm tap, shown in the page itself (not a browser pop-up), that says what will happen: "Move 3 tasks to Next and start fresh?" With Today empty: "Add the Minimum task and start fresh?" |
| D4 ✅ | Delete anything? | **Never.** Restart only moves tasks and adds one. |
| D5 ✅ | The word on the button? | **"Restart".** ("Reset" is already used for the Sunday Reset and the home reset.) Styled as a quiet secondary action. |

### E. Calendar

| # | Question | Decision |
|---|---|---|
| E1 ✅ | Which calendars? | One explicit list of calendar IDs in config: primary plus any others you list. Hidden duplicates (like the old Class Calendar) are left out by not listing them. Declined and cancelled events are hidden. All-day events show as plain lines above the timed list. An event that appears in two listed calendars shows once. Each listed calendar is one request to Google. |
| E2 ✅ | What's shown? | Today's events as a time list, with a "now" line and the Work Block highlighted. The Work Block is recognised by its **title from config** ("Work Block"), not by the 10:30 time. The highlight uses weight or a label as well as color. The "now" line moves on a one-minute timer in the page, without refetching. Events that have ended are dimmed. An empty day shows "Nothing on the calendar today." |
| E3 ✅ | Write to Calendar? | **Not in v1.** Read-only scope. Writing a "Hub" calendar for the Akimart is **v1.1** (see section 6). |
| E4 ✅ | Hide the dashboard before 10:30? | **No.** The dashboard is visible at all hours in v1. Hiding it wouldn't protect the phone-free morning, and it would hide the calendar at the desk. |

### F. Where it runs and who can open it

| # | Question | Decision |
|---|---|---|
| F1 ✅ | Hosting? | **One Cloudflare Worker** serves the page (static assets), the `/api/*` routes and the cron. This replaces the earlier "Worker + Pages" idea: one thing to deploy, and one place to protect. The Worker's code runs **before any static file is served**, so the page itself is behind the token check too. **Preview URLs are switched off**, so the one protected workers.dev address is the only way in. |
| F2 ✅ | Address? | The `*.workers.dev` address, behind Cloudflare Access, for now. It moves to `hub.josephmoto.com` after josephmoto.com is moved into the Cloudflare account (see section 6). |
| F3 ✅ | Who can open it? | Only you. **Cloudflare Access** (free Zero Trust plan), with a one-email policy. Sign-in goes through **GitHub as the identity provider** (the GitHub account has authenticator-app 2FA), not the emailed one-time code. GitHub is the only sign-in method offered for the hub. Session length is **one month**; all sessions can be ended from the Access dashboard at any time. The GitHub OAuth app's ID and secret for this live in Cloudflare Zero Trust, not in the Worker. |
| F4 ✅ | Defense if Access is bypassed? | The Worker checks the `Cf-Access-Jwt-Assertion` header on every request and rejects anything without a valid token for your email. It checks the signature against Access's public keys, plus the audience, issuer and expiry. If it can't fetch the keys, it rejects the request. The local-development skip only works when the request is to `localhost`. The team domain, audience tag and your email live in uncommitted Worker vars. |
| F5 ✅ | Routes that change data? | `POST` only: complete, add, restart. They require the Access JWT and a same-origin check: the `Origin` header must exactly match the hub's own address (a missing one is rejected), and the body must be JSON. |
| F6 ✅ | Which devices? | PC browser and phone browser. One layout for the desk monitor, readable from about 1 m, plus a phone layout. No installable app in v1. |
| F7 ✅ | What may the page load? | **Nothing from other sites.** No third-party scripts, fonts or analytics. Fonts are served from the hub itself. A strict Content-Security-Policy, and the page can't be embedded in other pages. |

### G. Logins and tokens (the security-critical part, built by the top model)

| # | Question | Decision |
|---|---|---|
| G1 ✅ | How do the hub's logins happen? | A one-time `/setup` page (behind Access) runs the OAuth "sign in with…" flow for TickTick and for Google. It shows "connected" or "not connected" for each service and nothing else about the tokens. Starting a login is a POST with the same checks as F5. Each service has a **Disconnect** button that revokes the token at the provider and deletes it from storage. |
| G2 ✅ | Where are tokens kept? | **Workers KV, encrypted** with AES-GCM (WebCrypto). The encryption key is a **Worker secret**. This is the deliberate exception to "stores no data." A fresh random nonce for every write. Each record is bound to its name, so the TickTick record can't be swapped in as the Google one. Each record carries a key-version label; changing the key means setting a new secret and reconnecting both services on `/setup`. |
| G3 ✅ | Other secrets? | Exactly five Worker secrets (`wrangler secret put`): TickTick client ID and secret, Google client ID and secret, and the token encryption key. Never in code, `wrangler.jsonc`, CLAUDE.md or chat. |
| G4 ✅ | Scopes? | TickTick: `tasks:read tasks:write`. Google: **`calendar.events.readonly`** only (narrower than `calendar.readonly`; the calendar IDs are in config, so the hub never lists calendars). |
| G4b ✅ | Google app status? | **"In production", unverified**, used only by you. You see a "Google hasn't verified this app" screen once when connecting. In "Testing" status the refresh token would expire every 7 days. |
| G5 ✅ | Refresh? | **Google:** connecting asks for offline access and consent, so a refresh token comes back. The cron uses it to mint short-lived access tokens (see G6c). If Google ever returns a new refresh token, the cron stores it. **TickTick:** no refresh in v1. The token is used until TickTick refuses it, then a "Reconnect TickTick" banner shows. TickTick's docs don't mention refresh tokens; on the first real login, note which fields the token response has (names only, never values) and decide then. |
| G6 ✅ | Logging? | Never log tokens, auth headers or full API responses. Never log task titles, event names or habit names. Log only status codes and timings. |
| G6b ✅ | OAuth callback safety? | **Required.** `state` stored server-side, single-use with a 10-minute TTL, tied to a `__Host-` SameSite=Lax HttpOnly cookie **and** the Access email. Fixed `redirect_uri`, PKCE checked. This stops login CSRF, where an attacker links *their* account to your hub. (From the independent review.) **PKCE is sent to both providers and tested during the build by trying a wrong verifier.** Where a provider ignores it, this doc says so plainly, and that login relies on the single-use `state`, the cookie, the Access email and the client secret. Neither provider's docs confirmed PKCE on 2026-11-14. |
| G6c ✅ | Two refreshes at once? | **Required.** KV is eventually consistent, so two refreshes could race and lose a rotated token. Refresh goes through **one place only: the cron** (no Durable Object). The cron runs every 20 minutes and mints a fresh Google access token each time; Google's access tokens last about an hour, so one failed run leaves no gap. Page requests only read the token and never refresh it. If the cron fails for a full hour, the calendar section shows its banner until the next run. On `invalid_grant`, re-read KV once before showing "Reconnect". (From the independent review.) |
| G7 ✅ | Local development? | `npm run dev` uses **fake data only**. No dev OAuth apps and no real tokens on the laptop. The real logins are tested on the deployed Worker, which is the only address the providers redirect to. The login code is covered by tests with mocked providers. `.dev.vars` holds only the local Access-skip setting, and Claude is blocked from reading it. |

### H. Data freshness and failure

| # | Question | Decision |
|---|---|---|
| H1 ✅ | When is data fetched? | **Live, with no stored cache.** That keeps "stores no data" true. Refresh happens on page load, on the refresh button, when the tab comes back into view, and every 10 minutes while the page is visible. The page shows "updated 9:41" so a stale page is obvious. |
| H2 ✅ | What's the cron for? | **Every 20 minutes** it mints the Google access token (G6c). **Once an hour** it also makes one small TickTick read to see if that token still works. Results go to the Worker's logs only, as status codes and timings. The page doesn't depend on those results; it finds out about a dead token on its own next load. |
| H3 ✅ | If TickTick or Google is down? | Show whatever loaded. A quiet banner: "TickTick didn't answer, tried 9:41." **Reads:** the page retries the failed section three times with growing gaps, then waits for the next regular refresh. **Writes** (complete, add, Restart): never retried automatically. You see "didn't save" and tap again, so nothing is done twice. |
| H4 ✅ | If a token expired? | Banner with a **Reconnect** button that goes to `/setup`. |
| H5 ✅ | Rate limits? | One request per upstream call needed (one per listed calendar) per refresh. Back off on a 429. |

### I. Quality and safety gates ✅

- Tests: Vitest with the Workers test pool. TickTick and Google are mocked. There is no automated live test (with Access in front it would need its own credential); a short manual checklist is run after each deploy.
- Each feature is built test-first (TDD skill).
- Before every merge: `/code-review medium`. For security-related branches, also `/code-review high` + `/security-review` (top model). Security-related means build steps 1, 2, 4 and 5 (section 5).
- On every pull request: gitleaks, osv-scanner, CodeQL, Dependabot, plus a CodeRabbit review (works because the repo is public).
- Done means: tests pass, typecheck passes, and the changed route was hit locally with `wrangler dev`.

## 3. API sketch

| Route | Method | Does |
|---|---|---|
| `/` | GET | Dashboard page |
| `/api/calendar` | GET | Today's calendar events |
| `/api/tasks` | GET | Today's unfinished tasks |
| `/api/habits` | GET | Weekly habit % |
| `/api/tasks/:id/complete` | POST | Complete a Today task. Always uses the Today project ID from config, so it can only complete tasks that are in Today. |
| `/api/next` | POST | Add a task to Next |
| `/api/restart` | POST | Move Today's leftovers to Next, add the Minimum task |
| `/setup` | GET | Shows whether TickTick and Google are connected |
| `/setup/connect/:provider` | POST | Start the login for TickTick or Google |
| `/setup/disconnect/:provider` | POST | Revoke the token at the provider and delete it |
| `/oauth/ticktick/callback`, `/oauth/google/callback` | GET | Finish OAuth (state + PKCE checked) |

The three GET routes are separate so each section loads and retries on its own, and a slow TickTick doesn't hold up the calendar.

"Today" everywhere means midnight to midnight in the configured time zone.

Config (non-secret, in `wrangler.jsonc` vars or KV): project IDs for Today and Next, habit IDs and display names, calendar IDs, Work Block title, priority-tag prefix and label (`JOB:` / "JOB" to start), Minimum task text, time zone `America/Indiana/Indianapolis`.

> Public-repo note: project, habit and calendar IDs aren't secrets, but keep them out of the repo anyway. Put them in Worker vars that aren't committed, or in KV.

### TickTick Open API facts (checked 2026-11-14 against `developer.ticktick.com/docs/openapi.md`)

| Need | What the docs say |
|---|---|
| Read Today | `GET /open/v1/project/{projectId}/data` returns the project's undone tasks, each with `sortOrder`. |
| Complete | `POST /open/v1/project/{projectId}/task/{taskId}/complete`. **No documented way to un-complete a task.** |
| Add to Next | `POST /open/v1/task` with `title` and `projectId`. |
| Restart's move | `POST /open/v1/task/move` with an array of `{fromProjectId, toProjectId, taskId}`. |
| Habit % | `GET /open/v1/habit/checkins?habitIds=…&from=YYYYMMDD&to=YYYYMMDD`. |
| Scopes | Only `tasks:read` and `tasks:write` are listed. The docs don't say which scope the habit endpoints need; **to confirm with a real token.** |
| Tokens | `refresh_token`, `expires_in` and PKCE are **not mentioned**. Token exchange uses Basic Auth with the client ID and secret. `POST /oauth/revoke` exists. |
| Rate limits | Not documented. |

### Google facts (checked 2026-11-14 against the Calendar API and Google OAuth docs)

| Need | What the docs say |
|---|---|
| Read events | `events.list` accepts `calendar.events.readonly` (view events on all your calendars), which is narrower than `calendar.readonly`. Google's scope page says to choose the most narrowly focused scope possible. |
| One day's events | `timeMin`, `timeMax`, `singleEvents=true`, `orderBy=startTime`, `timeZone`. Deleted events are left out by default. |
| Refresh token | Returned only on the first authorization, with `access_type=offline`. An app whose consent screen is in **"Testing"** status gets refresh tokens that **expire after 7 days**. A refresh token also stops working after six months without use, or if access is revoked. |
| Rotation | The docs don't say a refresh returns a new refresh token. |
| PKCE | Not mentioned in the part of the web-server flow page that could be read in full. **To confirm with a real test.** |

## 7. Smart layer (LATER, not v1, don't build now)

Built later with the Claude API and a scheduled agent, after v1 is used daily. Nothing in this section is part of v1.

- **Auto labels:** tags each task (JOB, CLASS, WORK, HOME, etc.) automatically.
- **Priority and due dates:** not every task needs one, but the smart layer may add them. There are two kinds of date. **Hard** dates (exams, meetings, anything clearly fixed) never move. **Soft** dates are flexible and can be set and adjusted automatically. Soft dates and priorities apply automatically and get reviewed in a batch at the Sunday Reset, not with one tap per task (to avoid accept-fatigue). No infinite to-do list.
- **Importance:** judged from context (what the task is, how I talk about it, what else is going on), not only from what I mark.
- **Objectives:** a word dump becomes one objective with steps inside it. Only its next step goes to Next. The hub gets an Objectives view I can click into.
- **Stuck tasks:** notices tasks sitting untouched. Based on its importance judgment it can shrink, re-rank or move low-importance ones automatically, and it suggests changes for important ones.
- **No pile-ups:** Today stays at 3. When Next gets crowded, low-importance items go back to Someday automatically.
- **Breakdowns:** splits big tasks into small first steps sized to the task. If there's a due date, steps are planned backward from it so the work fits before it's due, when possible.
- **ADHD strategies per task:** tiny first step, music during the task, body doubling, timers, "just start for a few minutes", environment setup. Usually avoid suggesting fun-before-boring or rewards-after-completion (they tend not to work for me), but this is not a strict ban.
- **Due-date awareness:** shows what's due soon. Restart flags due-soon tasks instead of quietly moving them. Helps decide skip or make-up when I fall behind.
- **Sunday Reset help:** reviews Someday, Scrap and stuck tasks, re-ranks priorities over time, and batch-reviews the auto-set dates.
- **Tone:** no guilt, ever.

**Open questions (decide when this is designed):**
- **Scrap area:** likely a separate Scrap spot on the hub for dumps that get turned into objectives, instead of filling Someday.
- **Calendar:** Today's max of 3 is for tasks only; calendar events are separate. Decide later whether task steps get placed on the calendar.

**v1 rules this would have to revisit (noted now so they aren't changed by accident):**
- "Stores none of your tasks, events or habit data": objectives, scrap dumps and importance judgments need a home, either inside TickTick or in hub storage.
- Task text would be sent to the Claude API, which is a new place the data goes.
- A4 says v1 only reads and completes; the smart layer edits, re-ranks and moves tasks on its own.
- D1 says Restart moves everything; the smart layer makes it flag due-soon tasks.
