# Life Hub v1: Design

**Status:** decisions settled by the owner on 2026-11-14 and revised on 2026-11-15 after the design review (reports in [`docs/reviews/`](../reviews/)). Everything is settled except the items in "To confirm during the build" (section 5). A decision that depends on one of those items says so in its row.

**What this file describes:** the target behaviour. The repo already holds starter code in `src/`, `public/` and `test/` that differs from it in places. Section 4 lists each difference and which side wins.

**Later versions** are in [`later.md`](later.md). Nothing there is part of v1.

## 1. What v1 is (and isn't)

**Why it exists:** a portfolio project that shows OAuth, security and testing work. It is not a productivity fix. The owner's routine (below) already works without it.

**Is:** one private web page showing five things:
1. Today's calendar
2. The TickTick **Today** list with checkboxes
3. A box to add a task to **Next**
4. Weekly habit percentages
5. A **Restart** button

**Isn't (later versions, see `later.md`):** the smart layer, editing task text, links to Claude projects, a chat panel, scrap pad, clickable flowcharts, project planner, smart devices, finances, n8n, NAS integration, phone app, notifications.

**How it is put together:** a browser page talks only to one Cloudflare Worker. The Worker checks who is asking, then reads and writes TickTick and reads Google Calendar on the owner's behalf.

**The routine this page sits on.** All of this already exists in TickTick and Google Calendar; the hub only shows it.
- **Today, Next, Someday:** three TickTick projects. Today holds at most 3 tasks ("limit 3"). Next holds what comes after. Someday holds ideas.
- **Morning routine:** when the owner picks the tasks for Today.
- **First-step format:** a task is written as one small first step with a done condition, for example `open resume doc (done = 1 application submitted)`.
- **Minimum task:** one fixed small task that Restart adds to Today (D2).
- **Habits:** three, tracked in TickTick: Job action, Phone-free morning, 15-min home reset.
- **Sunday Reset:** the owner's weekly review, on Sunday. It reads the week's habit numbers.
- **Work Block:** a calendar event with that title, at 10:30 when this was written. The phone-free morning comes before it.
- **Akimart:** the owner's desk calendar display. It shows the owner's Google Calendar only. Tasks are never entered there, and it can't load web pages.
- **The old Class Calendar:** _owner to fill in._
- **"From chat"** (B3): _owner to fill in which chat._

**Hard rules:**
- Reads TickTick and Google Calendar. **Stores no task, event or habit data.** The only things kept are encrypted provider tokens and a 10-minute login state in KV, plus logs of status codes and timings. If the hub is deleted, no task, event or habit data is lost; the Worker's settings (section 3) would have to be entered again and both services reconnected.
- No streaks anywhere. Percentages only, with a 70% target line.
- No notifications in v1.
- Unfinished Today tasks do not pile up. Restart sends them back to Next.

## 2. Decisions

Two words used throughout:
- **The owner** is the one person who uses the hub.
- **Quiet** means normal text colour, no red, no warning icon and no pop-up.

Capitalised **Today** always means the TickTick project. "The current day" means midnight to midnight in the configured time zone.

### A. The Today list

| # | Question | Decision |
|---|---|---|
| A1 | What counts as "Today"? | The TickTick **project named "Today"**, not TickTick's smart Today filter. The project is found by its **ID in config**, not by name. Show its top-level unfinished tasks in TickTick's manual order (`sortOrder`). Checklist items inside a task aren't shown. Tasks due on the current day in other projects aren't shown. |
| A2 | What if Today has more than 3 tasks? | Show them all, plus one quiet count line, only when over 3: "4 today · limit 3". |
| A3 | What does checking a box do? | Marks the task complete in TickTick. The row fades, and **Undo** shows for 5 seconds before the request is sent, so a mis-tap can be undone while the page stays open. Each task has its own timer. **While any completion is pending, automatic page refreshes are skipped, and the refresh button and Restart are disabled.** If the page is hidden or closed during the 5 seconds, the completion is sent at once. That send is best-effort: if it fails, the task shows as unfinished on the next load. If a normal send fails, the row comes back with a quiet "didn't save" note. (TickTick documents no way to un-complete a task, so waiting before sending is the undo.) |
| A4 | Can tasks be edited or reordered here? | **No.** Editing stays in TickTick. v1 only reads and completes. Tapping a task's text does nothing: no detail view, no link out. Editing task text on the hub is on the later list (`later.md`). |
| A5 | Show priority-tag tasks differently? | Yes. A small text tag in front, with the prefix hidden. The prefix (`JOB:`) and its label ("JOB") are **two named constants in one file** (`PRIORITY_TAG_PREFIX` and `PRIORITY_TAG_LABEL` in `src/domain/input.ts`), not settings. Changing the tag to `CLASS:` or `WORK:` later is a two-line code change. **One tag at a time in v1.** The match is the prefix at the start of the title, any letter case. |
| A6 | What if Today is empty? | One quiet line: "Today is clear." No button, no prompt to add more. The hub can't tell "all done" from "never picked", and the line covers both. |
| A7 | Show the done condition? | Yes. When a task's title has a `(done = …)` part (the first-step format), the title is shown without that part, and a second line under it reads "Done = …". A task without one shows no second line. The match ignores letter case and spaces around the `=`. |

### B. Add to Next

| # | Question | Decision |
|---|---|---|
| B1 | What does the box do? | Creates a task in the **Next** project. The text is trimmed, control characters are removed, and runs of spaces become one space. An empty box does nothing. Text over 300 characters is refused with a quiet note. The button is disabled while sending, so a double tap can't create two tasks. On success the box clears and a quiet "Added to Next" shows for 3 seconds; the hub doesn't show the Next list. On failure the text stays in the box with a quiet "didn't save" note. |
| B2 | Help with the first-step format? | Placeholder text: `open resume doc (done = 1 application submitted)`. A priority-tag toggle (labelled **JOB**; prefix and label are the constants in A5) adds the prefix in front unless the text already starts with it, and switches off after each add. No format validation. |
| B3 | Add to Today or Someday too? | **No.** Only Next. Today is chosen in the morning routine, and Someday ideas go in from chat. |

### C. Weekly habit %

| # | Question | Decision |
|---|---|---|
| C1 | Which habits? | The three: Job action, Phone-free morning, 15-min home reset. Their IDs **and display names are stored in config**, so the section needs one request (the check-ins). Renaming a habit in TickTick doesn't change the hub until config changes. |
| C2 | What's a "week"? | **Monday–Sunday**, so the week ends at the Sunday Reset. The current day and the week edges are worked out in `America/Indiana/Indianapolis` time. |
| C3 | How is % calculated? | **% so far this week.** A day counts as done when its check-in `value` reaches its `goal`. Percentage = done days ÷ (days already finished this week + the current day, if it is done). The current day is left out until it is done, so the number never drops for a day that isn't over. Monday before any check-in shows "—", not 0%. A missed Sunday is never counted in that week's figure (5 of 6 shows, not 5 of 7). Accepted. |
| C4 | How is it shown? | One bar per habit with a thin line at 70%, plus the numbers as text: "75% · 3 of 4 days". The bar doesn't change colour below 70%. No streak counts, no flames, no red. |
| C5 | What if OAuth can't read habits? | **Settled, pending the check at step 4.** TickTick's docs list only `tasks:read` and `tasks:write` and don't say what the habit endpoints need. If the OAuth token is refused, **habit % leaves v1** and step 7 becomes a removal step (section 5). No personal API token: it's a second, broader credential. |
| C6 | Check in habits from the hub? | **No.** Habits are read-only in v1. Check-ins happen in TickTick. |

### D. Restart

| # | Question | Decision |
|---|---|---|
| D1 | What does Restart do? | **End state:** Today holds only the Minimum task, and every other unfinished Today task is in Next. Restart (1) moves every unfinished Today task, except an existing Minimum task, to **Next**, one task per request; (2) adds one Minimum task to Today if none is there (same title); (3) shows "The system is back on." Rules: the Worker re-reads Today at the moment of Restart and doesn't trust the page's list. Restart is disabled while a completion is pending (A3). If some moves fail, the message gives the counts ("Moved 2, 1 didn't move. Try again."). If the add fails, the message says so ("Moved 3 tasks. Couldn't add the Minimum task."). Pressing Restart again does only what is left, and pressing it twice in a row changes nothing. With Today already empty, Restart adds the Minimum task. If the Minimum text in config changes while an old Minimum task is in Today, the old one is moved to Next like any other task. |
| D2 | Which Minimum task? | **One fixed line from config**, with no choice offered. Starting text: `JOB: open job board, save 1 posting (done = 1 saved)`. There is no default in code: without the setting, Restart answers `not_configured`. |
| D3 | Confirmation? | One confirm tap, shown in the page itself (not a browser pop-up): "Move unfinished tasks to Next and start fresh?" With Today empty: "Add the Minimum task and start fresh?" The question carries no count, because the Worker re-reads Today; the result message carries the real number. |
| D4 | Delete anything? | **Never.** Restart only moves tasks and adds one. |
| D5 | The word on the button? | **"Restart".** ("Reset" is already used for the Sunday Reset and the home reset.) Styled as a secondary action. |

### E. Calendar

| # | Question | Decision |
|---|---|---|
| E1 | Which calendars? | One explicit list of calendar IDs in config: primary plus any others the owner lists. Hidden duplicates (like the old Class Calendar) are left out by not listing them. Declined and cancelled events are hidden. All-day events show as plain lines at the top of the "Later today" card (E2). An event that appears in two listed calendars shows once. Each listed calendar is one request to Google. If one of them fails, the whole calendar request counts as failed, so the section never shows part of a day as if it were all of it. |
| E2 | What's shown? | Two places, in the chosen look (`DESIGN.md`). The **"Up next" banner** shows the next event of the current day with a countdown to its start. The **"Later today" card** lists the rest of the day's events after that one, in time order. **Past events are hidden**; an event is past once it has ended. With nothing left, the banner says "Nothing else today". An event that has started but not ended stays in the banner, with "now" in place of the countdown. All-day events are never the banner's event. The Work Block is recognised by its **title from config** ("Work Block"), ignoring letter case and spaces at the ends, not by the 10:30 time, and it is marked by weight or a label as well as colour wherever it shows. The countdown, and the step from one event to the next, run on a one-minute timer in the page, without refetching. |
| E3 | Write to Calendar? | **Not in v1.** Read-only scope. Writing a "Hub" calendar for the Akimart is v1.1 (`later.md`). |
| E4 | Hide the dashboard before 10:30? | **No.** The dashboard is visible at all hours in v1. Hiding it wouldn't protect the phone-free morning, and it would hide the calendar at the desk. |

### F. Where it runs and who can open it

| # | Question | Decision |
|---|---|---|
| F1 | Hosting? | **One Cloudflare Worker** serves the page (static assets) and every route. There is no cron (H2). This replaces the earlier "Worker + Pages" idea: one thing to deploy, and one place to protect. The Worker's code runs **before any static file is served**, so the page itself is behind the Access check too. **Preview URLs stay switched off.** The workers.dev address is switched on **only in the same step that puts Cloudflare Access in front of it** (step 1a); the deployed hub is never reachable without Access. This is the intended configuration; the exact settings are checked at step 1a. |
| F2 | Address? | The `*.workers.dev` address, behind Cloudflare Access. It moves to `hub.josephmoto.com` after josephmoto.com is moved into the Cloudflare account (`later.md`). |
| F3 | Who can open it? | Only the owner. **Cloudflare Access** (free Zero Trust plan), with a one-email policy. Sign-in goes through **GitHub as the identity provider**, not the emailed one-time code. The GitHub account must have authenticator-app 2FA. GitHub is the only sign-in method offered for the hub. Session length is **one month**; all sessions can be ended from the Access dashboard at any time. The GitHub OAuth app's ID and secret for this live in Cloudflare Zero Trust, not in the Worker. |
| F4 | Defense if Access is bypassed? | The Worker checks the `Cf-Access-Jwt-Assertion` header on every request and rejects anything without a valid Access token for the owner's email. It checks the signature against Access's public keys, plus the audience, issuer and expiry. If it can't fetch the keys, or any Access setting is missing, it rejects the request. The local-development skip works only when all of these hold: the skip flag is on, fake data is on, Access is not configured, the address is localhost, and the connecting IP is loopback. |
| F5 | Routes that change data? | **Every POST route** (complete, add, restart, connect, disconnect). Each requires the Access token and a same-origin check: the `Origin` header must exactly match the hub's own address (a missing one is rejected), and the body must be JSON (an empty object when there is nothing to send). "JSON" means all four: sent as exactly `application/json` (a charset parameter is allowed), valid UTF-8 with no byte order mark, a JSON object (not a list or a bare value), and at most 4096 bytes; nothing past that limit is read. |
| F6 | Which devices? | PC browser and phone browser. One layout for the desk monitor, readable from about 1 m, plus a phone layout. The page has a dark and a light look and follows the device's light or dark setting; there is no toggle in v1 (`DESIGN.md`). No installable app in v1. |
| F7 | What may the page load? | **Nothing from other sites.** No third-party scripts, fonts or analytics. Fonts are served from the hub itself. The Content-Security-Policy is the one already set in `src/index.ts` (`default-src 'self'`, no inline script, `frame-ancestors 'none'`), so the page can't be embedded in other pages. |

### G. Logins and tokens (the security-critical part)

"Sign-in" below means the owner's Access session. "Connection" means the hub's stored permission to use TickTick or Google. "Access token" with a capital A is Cloudflare's; "provider token" is TickTick's or Google's.

| # | Question | Decision |
|---|---|---|
| G1 | How are the connections made? | A `/setup` page (behind Access) runs the OAuth flow for TickTick and for Google. It shows "connected" or "not connected" for each service and nothing else about the tokens. Starting a connection is a POST with the F5 checks; the Worker answers with the provider's sign-in address and the page goes there. Each service has a **Disconnect** button that revokes the token at the provider and deletes it from storage. If the revoke call fails, the token is still deleted and the page says to remove the hub's access on the provider's own account page. |
| G2 | Where are provider tokens kept? | **Workers KV, encrypted** with AES-GCM (WebCrypto). KV is enough for two small records and adds no other service. The encryption key is a **Worker secret**. A fresh random nonce for every write. Each record is bound to its provider name, so the TickTick record can't be swapped in as the Google one. Each record starts with a format version (`v1` today). Changing the key means setting a new secret and reconnecting both services on `/setup`; old records then fail to decrypt and show "Reconnect". |
| G3 | Other secrets? | Five values are always Worker secrets (`wrangler secret put`): TickTick client ID and secret, Google client ID and secret, and the token encryption key. The Access audience tag and the owner's email are also set on Cloudflare, never in the repo (section 3). None of these go in code, `wrangler.jsonc`, CLAUDE.md or chat. |
| G4 | Scopes? | TickTick: `tasks:read tasks:write`. Google: **`calendar.events.readonly`** only (narrower than `calendar.readonly`; the calendar IDs are in config, so the hub never lists calendars). |
| G4b | Google app status? | **"In production", unverified**, used only by the owner. The owner sees a "Google hasn't verified this app" screen once when connecting. In "Testing" status the refresh token would expire every 7 days. |
| G5 | Refresh? | **On demand. No cron.** **Google:** connecting asks for offline access and consent, so a refresh token comes back. The stored record holds the access token, its expiry time and the refresh token. A calendar request that finds the access token expired uses the refresh token to get a new one, saves it, and carries on. If Google returns a new refresh token, that is saved too. If Google answers `invalid_grant`, the Worker re-reads KV once (a reconnect may have just happened); if it still fails, the record is deleted and the page shows "Reconnect Google". **TickTick: settled, pending the check at step 4.** If its token response includes a refresh token, refresh on demand the same way. If not, the token is used until TickTick refuses it, then the page shows a "Reconnect TickTick" button. |
| G6 | Logging? | Never log tokens, auth headers or full API responses. Never log task titles, event names or habit names. Log only status codes and timings. One exception, for the step 4 check: the field **names** of TickTick's token response, never the values. |
| G6b | OAuth callback safety? | The `state` value is stored in KV, single-use with a 10-minute TTL, tied to a `__Host-` SameSite=Lax HttpOnly cookie **and** the Access email. The `redirect_uri` is fixed. This stops login CSRF, where an attacker links *their* account to the owner's hub. A PKCE verifier is sent to both providers, but whether each provider enforces it is unconfirmed (section 5), so the login does not rely on it; it relies on the single-use `state`, the cookie, the Access email and the client secret. KV cannot read and delete in one step, so a `state` could in theory be used twice within a moment. Accepted: the second use would also need the owner's cookie and Access session. |
| G6c | Two refreshes at once? | **Allowed.** Two requests (say, PC and phone) can both find the Google token expired and both refresh. Each gets a valid access token, and the last one saved wins. That is safe as long as Google does not replace the refresh token on a refresh. Its docs don't say it does; this is checked at step 2, and if it does, this decision is reopened. A refresh in flight during a Disconnect can write the record back; the token was revoked at Google, so the next refresh gets `invalid_grant` and the record is deleted. |
| G7 | Local development? | `npm run dev` uses **fake data only**. No dev OAuth apps and no real provider tokens on the laptop. The real connections are tested on the deployed Worker, which is the only address the providers redirect to. The login code is covered by tests with mocked providers. `.dev.vars` holds only the local Access-skip settings, and the builder is blocked from reading it. |

### H. Data freshness and failure

| # | Question | Decision |
|---|---|---|
| H1 | When is data fetched? | **Live, with no stored cache.** That keeps the "stores no task, event or habit data" rule true. Data is fetched on page load, on the refresh button, when the tab comes back into view, and every 10 minutes while the page is visible. Each section shows the time of its last good load ("updated 9:41"), so the data's age is visible. Automatic refreshes are skipped while a completion is pending (A3). |
| H2 | Is there a cron? | **No.** v1 has no scheduled job. The Google token is refreshed on demand (G5), and the page finds out about a refused provider token on its own next load. A health check can come back in v1.1, when something reads its result (`later.md`). |
| H3 | If TickTick or Google is down? | **Reads:** the failed section keeps its last loaded data on screen (in page memory only) with a quiet "couldn't update" note and the time of the last good load. There is no automatic retry; the next regular refresh or the refresh button tries again. A section that has never loaded shows "couldn't load" where its data would be. **Writes** (complete, add, Restart): the hub never repeats a write on its own. The owner sees "didn't save" and taps again. Complete and Restart are safe to repeat. Add to Next is not: if TickTick saved the task but the answer was lost, a second tap adds a duplicate. Accepted. |
| H4 | If a provider token is missing or refused? | Banner with a **Reconnect** button that goes to `/setup`. |
| H5 | Rate limits? | One request per upstream call (one per listed calendar) per refresh. With no automatic retries, a 429 is treated like any other failure (H3). |
| H6 | If the owner's sign-in has ended? | One page-level "Sign in again" link that reloads the page. Sections don't show "couldn't update" and writes don't show "didn't save" for this case. Text typed in the add box stays until the reload. |

### I. Quality and safety gates

- **Tests:** Vitest with the Workers test pool. TickTick and Google are mocked. There is no automated live test (with Access in front it would need its own credential). A manual checklist is run after each deploy; it is written in step 1a as `docs/deploy-checklist.md`.
- **The page:** plain HTML, CSS and JavaScript in `public/`, with no framework and no build step. Page logic that can go wrong (undo timers, the blocking rule, what each response means) lives in `public/hub-logic.js` as functions that don't touch the page, so Vitest can test them.
- **Login code:** written by hand with `fetch` and WebCrypto. No new dependency; `jose` is already used for the Access token check.
- **Who builds, test-first work, review commands and "done means":** see [`CLAUDE.md`](../../CLAUDE.md). The security-related steps are 1a, 2, 4, 5, 6 and 8 (section 5).
- **On every pull request,** CI (`.github/workflows/ci.yml`) runs the typecheck, the tests, `npm audit` on production dependencies (high severity and above) and gitleaks. Dependabot version updates are configured in `.github/dependabot.yml`. CodeQL and Dependabot alerts are GitHub repository settings (runbook step 4), not workflow files. osv-scanner is not set up. CodeRabbit is optional and may not be installed.

### J. Limits accepted

- The Cloudflare account and the GitHub account are what everything rests on. Whoever controls the Cloudflare account can read both the encryption key and the encrypted provider tokens, so the KV encryption protects against a leak of KV contents alone, not against a takeover of the account.
- An Access session lasts one month, and the page can complete, add and move TickTick tasks. Someone holding an unlocked, signed-in device can do those things until the session is ended from the Access dashboard. They cannot delete tasks (D4).
- The real connections run only on the deployed Worker (G7). The login code is covered by mocked tests plus one manual check per provider after deploy.
- Smaller accepted risks are stated where they apply: a duplicate from Add to Next (H3), a `state` used twice within a moment (G6b), a missed Sunday in the weekly figure (C3).

## 3. Routes, responses, configuration and API facts

### Routes

| Route | Method | Does |
|---|---|---|
| `/` | GET | Dashboard page |
| `/api/calendar` | GET | The current day's calendar events |
| `/api/tasks` | GET | Today's unfinished tasks, the priority-tag label, and which write routes are switched on |
| `/api/habits` | GET | Weekly habit % |
| `/api/tasks/:id/complete` | POST | Complete a Today task. The Worker first re-reads Today and refuses a task that isn't in it. |
| `/api/next` | POST | Add a task to Next |
| `/api/restart` | POST | Move Today's leftovers to Next, add the Minimum task |
| `/setup` | GET | Shows whether TickTick and Google are connected. Rendered by the Worker; its script is the static file `public/setup.js`. |
| `/setup/connect/:provider` | POST | Start a connection; answers with the provider's sign-in address |
| `/setup/disconnect/:provider` | POST | Revoke the provider token and delete it |
| `/oauth/ticktick/callback`, `/oauth/google/callback` | GET | Finish a connection: `state` verified by the Worker, PKCE verifier sent |

The three `/api` GET routes are separate so each section loads on its own, and a slow TickTick doesn't hold up the calendar. Each needs only its own provider and its own settings: the calendar works before TickTick is connected.

### What each answer means to the page

| The Worker answers | Meaning | The page shows |
|---|---|---|
| The hub's own 401 or 403 (except a 403 with `{"error":"cross_site"}`, which is a failure: last row and step 1b), or the request is sent to the Access sign-in page | The owner's sign-in has ended | One page-level "Sign in again" link that reloads (H6) |
| `not_connected` with a provider name | That provider token is missing or was refused | "Reconnect" banner for that provider (H4) |
| `not_configured` | A setting that section needs is missing | A fixed "not set up yet" line in that section |
| `not_enabled` (write routes only) | That write route is not switched on yet (section 5) | Nothing: the control is hidden, because `/api/tasks` already said so |
| Anything else, or no answer | A failure | Reads: "couldn't update" with the last data and time. Writes: "didn't save" (H3) |

### Configuration

- **Committed in `wrangler.jsonc`:** vars: only `TIME_ZONE` (`America/Indiana/Indianapolis`) and `USE_FAKES`; the KV namespace ID may be committed (not a secret). Wrangler writes that ID into `wrangler.jsonc` when it creates the namespace at the first deploy.
- **Set on Cloudflare as Worker vars or secrets, never in the repo:** everything else.

| Setting | Name | Form |
|---|---|---|
| Access team domain, audience tag, owner's email | `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `ALLOWED_EMAIL` | text |
| Token encryption key | `TOKEN_ENC_KEY` | secret, base64, 32 bytes |
| Provider client IDs and secrets | `TICKTICK_CLIENT_ID`, `TICKTICK_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | secrets |
| The hub's own address (for the fixed `redirect_uri`) | `HUB_ORIGIN` | text |
| Today and Next project IDs | `TICKTICK_TODAY_PROJECT_ID`, `TICKTICK_NEXT_PROJECT_ID` | text |
| Minimum task text | `MINIMUM_TASK_TEXT` | text |
| Habit IDs and display names | `HABITS` | JSON text: `[{"id":"…","name":"…"}]` |
| Calendar IDs | `CALENDAR_IDS` | JSON text: `["…"]` |
| Work Block title | `WORK_BLOCK_TITLE` | text |
| PKCE wrong-verifier test (steps 2 and 4 only; unset at all other times) | `PKCE_TEST_WRONG_VERIFIER` | text; on only when exactly `true` |

`HABITS` replaces the starter's `TICKTICK_HABIT_IDS` in step 7; until then the code still reads `TICKTICK_HABIT_IDS`. A missing or badly formed setting switches off only the section that needs it (`not_configured`).

Local development reads the Access-skip settings from `.dev.vars` (never committed); `.dev.vars.example` shows the names.

### TickTick Open API facts (checked 2026-11-14 against the TickTick Open API docs linked in `CLAUDE.md`; the page read was `developer.ticktick.com/docs/openapi.md`)

| Need | What the docs say |
|---|---|
| Read Today | `GET /open/v1/project/{projectId}/data` returns the project's undone tasks, each with `sortOrder`. |
| Complete | `POST /open/v1/project/{projectId}/task/{taskId}/complete`. **No documented way to un-complete a task.** |
| Add to Next | `POST /open/v1/task` with `title` and `projectId`. |
| Restart's move | `POST /open/v1/task/move` with an array of `{fromProjectId, toProjectId, taskId}`. v1 sends one task per call, so a failure is counted per task. |
| Habit % | `GET /open/v1/habit/checkins?habitIds=…&from=YYYYMMDD&to=YYYYMMDD`. No documented way to undo a check-in. |
| Scopes | Only `tasks:read` and `tasks:write` are listed. The docs don't say which scope the habit endpoints need. |
| Tokens | `refresh_token`, `expires_in` and PKCE are **not mentioned**. Token exchange uses Basic Auth with the client ID and secret. `POST /oauth/revoke` exists. |
| Rate limits | Not documented. |

### Google facts (checked 2026-11-14 against the Calendar API and Google OAuth docs linked in `CLAUDE.md`)

| Need | What the docs say |
|---|---|
| Read events | `events.list` accepts `calendar.events.readonly` (view events on all the owner's calendars), which is narrower than `calendar.readonly`. Google's scope page says to choose the most narrowly focused scope possible. |
| One day's events | `timeMin`, `timeMax`, `singleEvents=true`, `orderBy=startTime`, `timeZone`. Deleted events are left out by default. |
| Access token | The token response gives its lifetime in `expires_in`. The Worker stores the expiry from that value and assumes no fixed length. |
| Refresh token | Returned only on the first authorization, with `access_type=offline`. An app whose consent screen is in **"Testing"** status gets refresh tokens that **expire after 7 days**. A refresh token also stops working after six months without use, or if access is revoked. |
| Rotation | The docs don't say a refresh returns a new refresh token. |
| PKCE | The web-server flow page was only partly retrieved. PKCE support is unverified. |

## 5. Build order (one branch per step)

**Rules for every step**
- Test-first. The step's tests are written or rewritten before the code.
- `npm test` and `npm run typecheck` pass, and the changed routes are hit locally with `npm run dev` on fake data. That is the "done when" baseline; each step adds its own line.
- Deploys, secrets and settings on Cloudflare are **owner tasks**. The builder never deploys or sets them without asking (`CLAUDE.md`). Account steps follow [`docs/setup-runbook.md`](../setup-runbook.md).
- A step marked **security-related** gets `/code-review high` and `/security-review` in addition to `/code-review medium`, before merge.
- The Access check, the POST checks, and the token and login code (in steps 1a, 2 and 4) are written by the top model tier named in `CLAUDE.md`.

**How write routes stay off until they are reviewed.** In step 1a the task interface is split into a read part and a write part. With fake data both parts exist. The real TickTick client, added in step 4, has the read part only. Until a write route's own step merges, that route answers `not_enabled` (status 503) on the deployed Worker and the page hides its control. The gate is checked before the provider connection and the settings, so the answer is `not_enabled` even when TickTick is not connected. The gate is per route: a route runs only when the write methods it needs are switched on (complete needs complete; add needs create; Restart needs move and create). So switching on complete in step 5 leaves add and Restart off, and Restart stays off until step 8 adds move. One function, `resolveTaskWrites` in `src/api.ts`, decides which methods are on. Each of steps 5, 6 and 8 adds one real write method and switches on one route, after its tests and its security review. No write reaches the real TickTick account before then.
